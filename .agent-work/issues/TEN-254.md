# TEN-254 — [P2] A gateway that answers with a different model id makes every judging re-run re-bill and double-count
status: Backlog
url: https://linear.app/tenken/issue/TEN-254/p2-a-gateway-that-answers-with-a-different-model-id-makes-every

**What breaks.** The re-run skip compares the REQUESTED model id, but the stored row carries the ANSWERING model id, and the unique key includes `model_id`. Against a gateway that version-pins (for example `x/y` answering as `x/y-2026-01`), no re-run ever skips: every pass re-bills the jury AND writes extra rows, and the aggregate sums all rows for a dimension, so the score moves.

**Evidence.**

* `packages/backend/src/judging/worker.ts:291-292` skips on the requested id.
* `packages/backend/src/judging/worker.ts:307` and `packages/backend/src/judging/model.ts:341` store the answering id.
* `packages/backend/src/judging/store.ts:96-99` unique key includes `model_id`.
* `packages/core/src/judgments.ts:96-113` sums all rows for a dimension, so an extra row changes the aggregate rather than being ignored.
* The README states the opposite: "a retry re-uses the stored evidence and calls no model".
* Combines with the non-atomic lease and the re-claim loop, and there is no per-day spend alarm.

**Blast radius.** Judge spend and score stability on any gateway that does not echo the requested id verbatim. OpenRouter-style gateways commonly do not.

**How we know it is fixed.** The skip and the unique key use the same id, a re-run against a gateway that renames the model calls no model, and the aggregate is unchanged.
