# TEN-247 — [P1] GET /api/site/:digest/* bypasses apiRoute, so it has no rate limit and takes one pool client per asset
status: Backlog
url: https://linear.app/tenken/issue/TEN-247/p1-get-apisitedigest-bypasses-apiroute-so-it-has-no-rate-limit-and

**What breaks.** The T1 site serving routes call `withApiContext` directly rather than going through `apiRoute`. They get no rate limit, not even the anonymous shared ceiling, and every asset of a hosted candidate site is one anonymous request, one Postgres round trip and one pool checkout. A site may carry up to 500 assets. This is the exact second-path pattern that <issue id="042ab382-b724-4b39-b8bd-f42f14cb0fad" href="https://linear.app/tenken/issue/TEN-107/two-public-pages-are-broken-on-staging-gallery-sends-a-query-the">TEN-107</issue> fixed for the share route, still open here. `/readyz` has the same shape.

**Evidence.**

* `services/api/src/app.ts` (route table at the end of `createApp`): the two site routes call `serveSite(...)`, and `serveSite` calls `withApiContext(...)` directly, not `apiRoute`.
* `packages/backend/src/t1/handlers.ts` `handleServeSite` runs one `SELECT 1 FROM attempt_site_claims WHERE digest = $1 LIMIT 1` per asset before the bytes are read.
* The share route's own comment in the same file records that this pattern was the <issue id="042ab382-b724-4b39-b8bd-f42f14cb0fad" href="https://linear.app/tenken/issue/TEN-107/two-public-pages-are-broken-on-staging-gallery-sends-a-query-the">TEN-107</issue> defect: a second path into the service with its own body handling and no rate limit.
* `packages/contract/src/t1.ts` `T1_LIMITS.maxFiles = 500`.
* `services/api/src/context.ts:112` `DEFAULT_POOL_MAX = 3`; `infra/terraform/variables.tf` `pg_pool_max` / `concurrency` = 8.
* `/readyz` is also anonymous and unlimited and runs `ctx.db.query("select 1")` on a checked-out client.

**Blast radius.** All candidates on the instance. One published gallery card that links a site, or one crawler, drains the pool; pool exhaustion 500s after the 10 s acquire timeout, so a sitting in progress fails to append its log.

**How we know it is fixed.** The site routes and `/readyz` go through one adapter that applies a limit, or the digest reachability check is served without a pool client, and a test asserts no route reaches `withApiContext` outside `apiRoute`.
