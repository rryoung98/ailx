# TEN-256 — [P2] Migrations run in one transaction with non-concurrent CREATE INDEX and full-table backfills
status: Backlog
url: https://linear.app/tenken/issue/TEN-256/p2-migrations-run-in-one-transaction-with-non-concurrent-create-index

**What breaks.** Migrations are applied `singleTransaction` with no `lock_timeout`. They contain full-table backfills and non-concurrent `CREATE INDEX`. That is safe on today's small tables and becomes a deploy-time stall that blocks every write once the tables are real-sized, because the migrate job runs before the traffic switch.

**Evidence.**

* `db/migrate.ts` applies with `singleTransaction`; no `lock_timeout` is set (see the related timeout finding).
* `db/migrations/0012_*.sql` backfills every `share_links` row with an `UPDATE`.
* `db/migrations/0007_*.sql` scans all of `responses`.
* `db/migrations/0009` through `0013` create indexes without `CONCURRENTLY`.
* The migrate job runs to completion before the Cloud Run traffic switch (`infra/cloudbuild/release.sh`), so a stalled migration is a stalled deploy with the old revision still serving.
* Verified CLEAN: migrations are forward-only with unique numeric prefixes and a `checkOrder` gate; the baseline path verifies every relation before fake-recording `0000`; new constraints on existing tables are added `NOT VALID` (`0002`, `0008`); `0008`'s DELETEs copy verbatim to `archive.*` first, have a working Down, and abort via `RAISE EXCEPTION` if a credential holder is ever in scope.

**Blast radius.** A future migration on a large table blocks writes for its whole duration, inside a deploy window.

**How we know it is fixed.** The migrate session sets a `lock_timeout`, index creation is `CONCURRENTLY` outside the single transaction, and a backfill on a large table is batched.
