# TEN-253 — [P2] assertJudgmentsAttested runs only in the browser, so the server checks no attestation on write
status: Backlog
url: https://linear.app/tenken/issue/TEN-253/p2-assertjudgmentsattested-runs-only-in-the-browser-so-the-server

**What breaks.** The attested-judgments invariant is enforced in the browser session engine and nowhere on the server write path. `judgmentIds` are written into the score row and are never recomputed or compared by any file in `packages/backend/src`. Nothing stops judgment rows being added after a score of record is issued, so a stored score can silently stop matching a recompute from stored inputs. This is the invariant that separates re-scoring from re-judging, and on this side of the boundary it is asserted, not enforced.

**Evidence.**

* `packages/backend/src/judging/worker.ts:362` and `packages/backend/src/finalize.ts:306` WRITE `judgmentIds`.
* `grep -rn 'assertJudgmentsAttested' packages/backend/src` returns nothing. The function exists only in `packages/session/src/machine.ts:257` and `:417` (the browser engine) and in tests.
* No file in `packages/backend/src` recomputes `judgmentId()` from stored rows and compares it to the claimed list on read.
* `judgments` has no constraint tying a row to a point in time relative to a `scores` row, so a later insert changes what a recompute would produce while the stored score stays.
* The order-invariance half IS enforced: `packages/core/src/judgments.ts` aggregates order-invariantly and the custody comparisons in `packages/backend/src/custody.ts` do run on both write and read.

**Blast radius.** Every judged score of record. The claim that any issued score is byte-identically recomputable from stored inputs is not checkable server-side today.

**How we know it is fixed.** The score write recomputes `judgmentId()` for each row it replayed and refuses a mismatch, `readScoresOfRecord` re-checks the same list, and a test that inserts an extra judgment after a score makes the read report the score unverifiable.
