# TEN-245 — [P1] No rate limit on any authenticated write route, including the 25 MB T1 upload
status: Backlog
url: https://linear.app/tenken/issue/TEN-245/p1-no-rate-limit-on-any-authenticated-write-route-including-the-25-mb

**What breaks.** For a signed-in caller everything except score, finalize and the model proxy is unbounded: attempt creation, log appends, transcript appends, the 25 MB site upload, share and credential writes, practice starts, and the attempt read the browser polls every 5 seconds. There is no per-attempt row cap either, so one account can grow the append-only table that the anonymous aggregates route scans.

**Evidence.**

* `services/api/src/context.ts` `rateVerdict()`: for `identity !== null` the rule comes only from `opts.limit` or `opts.publicRead`; with neither it returns `null`, meaning no limit. In `services/api/src/app.ts` only `/finalize` and `/score` pass `SCORE_RATE_LIMIT` and the six `/v1/model/*` routes pass their own.
* `packages/backend/src/store.ts:800` inserts one row per request; the only bound is `MAX_JSON_BODY_BYTES = 1024 * 1024` (`context.ts:52`) and `assertSeq` (`store.ts:83`), which accepts any non-negative 32-bit integer. So one attempt may hold up to 2^31 rows of up to 1 MiB.
* Live proof the client picks its own seq: `max(seq)` in `responses` is `1073741824` (2^30).
* `responses.payload` is `jsonb` with no size CHECK. `moderation_comments.body` and `profiles.display_name` are unbounded `text` in the database; `COMMENT_BODY_MAX` is applied only in `packages/contract/src/moderation.ts:126`.
* The upload is the worst case: `POST /v1/attempts/:id/site` is registered with `{ rawBody: true }` and no `limit`; `readCappedBody` buffers up to `T1_LIMITS.maxTotalBytes` = 25 MiB (`packages/contract/src/t1.ts:13`) into one array, and `packages/backend/src/t1/zip.ts` inflates it with `inflateRawSync` on the event loop of a 1-vCPU container, up to 500 entries.
* Nothing deletes: `responses`, `transcripts`, `practice_answers`, `moderation_comments`, `funnel_events` and `attempt_track_events` all document "never deleted" and there is no retention job in the repo.

**Blast radius.** One account can pin an instance's CPU with repeated uploads, and can make the public aggregates route arbitrarily expensive for everybody by growing `responses`.

**How we know it is fixed.** Every write route carries a rule, the polled attempt read carries one sized for the 5 s cadence, a per-attempt row ceiling exists, and a test enumerates the route table and fails on a write route with no limit (same shape as the existing public-route enumeration test).
