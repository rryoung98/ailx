# TEN-243 — [P1] attempts.participant_id and judgments(attempt_id, track_id) have no index
status: Backlog
url: https://linear.app/tenken/issue/TEN-243/p1-attemptsparticipant-id-and-judgmentsattempt-id-track-id-have-no

**What breaks.** Two tables that grow with every candidate are read on hot paths with a sequential scan. `attempts` is the parent every authenticated read reaches through; `judgments` is scanned up to three times per `GET /v1/attempts/:id`, which is the 5-second poll the report runs while judging is pending.

**Evidence.**

* `db/migrations/0000_baseline.sql` and `db/schema.sql` create no index on `attempts(participant_id)`. `judgments` has only `UNIQUE (submission_id, dimension, sample, rubric_version, model_id)`, which cannot serve a lookup by `attempt_id`.
* Live `pg_stat_user_tables` for `public.attempts` with only 10 live rows: `seq_scan = 3005`, `idx_scan = 918`, `seq_tup_read = 95889`. For `public.judgments`: `seq_scan = 255`, `idx_scan = 0`. Stats have never been reset.
* `EXPLAIN (ANALYZE)` on the gallery tier predicate (`packages/backend/src/profile.ts:469`, run on every signed-in `GET /v1/gallery`): `Seq Scan on attempts a ... Rows Removed by Filter: 2000` on a 2000-attempt replay.
* `EXPLAIN (ANALYZE)` on `packages/backend/src/store.ts:483` / `:515` (`getJudgments`, `getJudgmentRubricVersions`, reached via `trackCustody`): `Seq Scan on judgments j ... Rows Removed by Filter: 23988` to return 12 rows.
* `packages/backend/src/scoresOfRecord.ts` `JUDGING_POLL_INTERVAL_MS = 5_000`, and `trackCustody` runs once per track.
* No table in `public` has ever been analyzed or autovacuumed (`last_autovacuum IS NULL`, `last_analyze IS NULL` for every table).

**Recommended (no migration written here):** `attempts (participant_id, finalized_at)`, `judgments (attempt_id, track_id)`, and `attempt_site_claims (response_id)` for the FK check.

**Blast radius.** Every signed-in page read and every judging poll degrades linearly with total attempts across ALL candidates, not with the caller's own. At 50 concurrent sittings polling at 5 s that is 10 requests/second each scanning `judgments` three times.

**How we know it is fixed.** `CREATE INDEX CONCURRENTLY` for the three columns, both `EXPLAIN`s above show an Index Scan, and `seq_scan` on `attempts` stops climbing with traffic.
