# TEN-242 — [P1] No statement_timeout and no lock_timeout anywhere, so one slow query pins a pool slot with no end
status: Backlog
url: https://linear.app/tenken/issue/TEN-242/p1-no-statement-timeout-and-no-lock-timeout-anywhere-so-one-slow-query

**What breaks.** Nothing bounds how long a single statement may run. The handler holds one pool client for its whole duration, so a query that goes linear on a growing table, or a `FOR UPDATE` waiting behind another transaction, removes a connection from a pool of 3 (or 8) for as long as it takes. There is no ceiling and no error to alert on.

**Evidence.**

* Live `pg_settings` on the production database: `statement_timeout = 0`, `lock_timeout = 0`, `max_connections = 112`. `pg_db_role_setting` is EMPTY, so no per-role or per-database default is set either.
* Repo grep for `statement_timeout` / `lock_timeout` / `idle_in_transaction` across `*.ts`, `*.sql`, `*.tf` returns nothing in any source file. `poolConfig` (`services/api/src/context.ts:98-110`) sets only `idleTimeoutMillis` and `connectionTimeoutMillis`, which are client-side.
* `infra/terraform/variables.tf` states the design plainly: the pool IS the instance's real request concurrency.

**Blast radius.** Whole service. It is the reason the unbounded scans and the judging checkout have no natural end.

**How we know it is fixed.** `poolConfig` sets `options: '-c statement_timeout=... -c lock_timeout=...'` (with a longer explicit budget for the judging session), and a deliberately slow query returns SQLSTATE `57014` instead of holding a connection.

*Filed from a read-only review of* `ailx-backend` *@* `72db4e6` *(main), 2026-09-07.*
