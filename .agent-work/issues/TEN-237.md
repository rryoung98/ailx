# TEN-237 — [P0] resilient-staging serves assert-only dev auth on a service bound to allUsers
status: In Review
url: https://linear.app/tenken/issue/TEN-237/p0-resilient-staging-serves-assert-only-dev-auth-on-a-service-bound-to

**What breaks.** `resilient-staging` runs `AILX_AUTH=dev`, so one request header IS any participant. That includes the six `/v1/model/*` routes, which spend the provider key sealed against that identity. This is the <issue id="3a338b1d-b8f0-4092-ad54-b68d46aa29c3" href="https://linear.app/tenken/issue/TEN-108/critical-staging-cloud-run-runs-asserted-dev-auth-with-allusers">TEN-108</issue> incident repeated on the new project.

**Evidence.**

* `infra/terraform/env/resilient-staging.tfvars:14` `auth_mode = "dev"`.
* `infra/terraform/run.tf:38-40` auto-injects `AILX_ALLOW_INSECURE_DEV_AUTH = "1"` whenever `auth_mode == "dev"`. That cancels the guard in `packages/backend/src/auth.ts:117-124` that otherwise refuses dev auth under `NODE_ENV=production`.
* `infra/terraform/run.tf:260` binds `allUsers` to `roles/run.invoker`.
* Measured read-only on 2026-09-07: `GET /v1/progress` with an asserted `x-ailx-dev-user` header against `https://ailx-backend-106323225578.us-central1.run.app` returned **200** with a full progress payload. The same request against the live `tenken-staging` service returned **401**.
* `infra/terraform/env/staging.tfvars:11` records the identical prior incident (<issue id="3a338b1d-b8f0-4092-ad54-b68d46aa29c3" href="https://linear.app/tenken/issue/TEN-108/critical-staging-cloud-run-runs-asserted-dev-auth-with-allusers">TEN-108</issue>).

Note: the probe may have created one participant row keyed `review-probe` on that service.

**Blast radius.** Anyone who can reach that URL. It is the deployment Terraform actually applies to, so it is the one the frontend is most likely pointed at next.

**How we know it is fixed.** `resilient-staging.tfvars` says `auth_mode = "clerk"`, or `run.tf` stops auto-injecting `AILX_ALLOW_INSECURE_DEV_AUTH`, and the same probe returns 401.
