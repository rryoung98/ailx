# TEN-183 — [P0] Board calls to Linear carry no abort signal, so a slow Linear hangs the board
status: Backlog
url: https://linear.app/tenken/issue/TEN-183/p0-board-calls-to-linear-carry-no-abort-signal-so-a-slow-linear-hangs

**What breaks.** `lib/linearBoard.ts:190` calls `fetchImpl(LINEAR_ENDPOINT, ...)` with no `signal` and no timeout, reached from `:233`, `:239` and `:291`. `loadBoard` pages sequentially up to `BOARD_MAX_PAGES = 20` (`:238`), so the worst case is 21 chained unbounded awaits.

**Evidence.** `lib/linear.ts:227` already does this correctly with `AbortSignal.timeout(SPRINT_TIMEOUT_MS)`; the board module never got it. `app/api/board/move/route.ts:52` awaits `readBoard()` before the mutation, so a drag hangs on the same read.

**Blast radius.** `/board`, `GET /api/board`, `POST /api/board/move`.

**How to know it is fixed.** `callLinear` takes the same abort signal as the sprint read. With a fetch stub that never resolves, `readBoard()` reaches its error state inside the deadline.
