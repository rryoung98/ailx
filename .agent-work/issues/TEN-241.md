# TEN-241 — [P1] A judging run killed mid-pass is re-claimed for ever because tries is never incremented on claim
status: Backlog
url: https://linear.app/tenken/issue/TEN-241/p1-a-judging-run-killed-mid-pass-is-re-claimed-for-ever-because-tries

**What breaks.** `tries` is incremented only by `recordJudgingOutcome`. A process killed mid-pass never records an outcome, so `MAX_TRIES = 3` never applies and the row is re-claimed indefinitely. The kill is routine, not exceptional: the worst-case drain is 5 attempts x 2 tracks x 3 jury x 3 retries x 120 s = 10800 s against a job timeout of 1800 s with `max_retries = 0`. The candidate sees `pending_judging` for ever, which is the original spinner defect under a new state name.

**Evidence.**

* `packages/backend/src/judging/queue.ts:196-240` `recordJudgingOutcome` is the only writer of `tries`; `claimAttemptForJudging` (`queue.ts:157-186`) does not touch it.
* `infra/terraform/judging.tf:39-43` job `timeout = 1800s`, `max_retries = 0`.
* `packages/backend/src/judging/model.ts:125` `timeoutMs: 120_000, maxRetries: 2`.
* `packages/backend/src/scoresOfRecord.ts:338-341` reports a `pending` run as `pending_judging` with a poll interval, so the client keeps asking.
* There is also no spend ceiling per attempt, per drain or per day: only a batch COUNT bounds cost (`packages/backend/src/judging/judge.ts:100`). A re-claim loop therefore has no cost backstop and no alarm.

**Blast radius.** Any attempt whose pass exceeds the job timeout. It never terminates, it re-bills the jury on every drain, and the candidate is never told.

**How we know it is fixed.** `tries` is incremented at claim time (or the lease expiry counts as a try), a row that exceeds `MAX_TRIES` becomes terminal `failed`, and a killed run reaches `failed` after three drains rather than looping.
