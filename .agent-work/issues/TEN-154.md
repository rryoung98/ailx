# TEN-154 — A Vercel preview cannot verify any hosted-mode change: no preview env vars, deployment protection on, and the service's CORS allowlist names only staging
status: Backlog
url: https://linear.app/tenken/issue/TEN-154/a-vercel-preview-cannot-verify-any-hosted-mode-change-no-preview-env

Found while trying to verify PR #46 against a Vercel PREVIEW. The preview cannot test anything
that talks to the exam service, for three independent reasons. Any one of them alone would be
enough.

1. **The Preview environment has no environment variables.** `vercel env ls` on `ailx-staging`
   shows every variable scoped to **Production only** — `AILX_BACKEND`, `NEXT_PUBLIC_AILX_API_BASE`,
   `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `AILX_AUTH`, all of them. The single exception is
   `BLOB_READ_WRITE_TOKEN`. So a preview builds WITHOUT `AILX_BACKEND=1`: it has none of the seven
   database-reading pages, no API base and no Clerk. It is a different product.
2. **Deployment Protection is on.** The preview alias redirects a browser to `vercel.com/login`,
   so no agent and no reviewer can open it without a Vercel session or an automation bypass token.
   No bypass secret is configured.
3. **The service's CORS allowlist names two origins.** Cloud Run `AILX_ALLOWED_ORIGINS` is
   `https://rryoung98.github.io,https://ailx-staging.vercel.app`. A preview URL is neither, so
   every authenticated call from a preview would be blocked at the preflight even with the env
   vars and the protection sorted.

**Consequence.** No frontend change that touches the hosted mode can be proven before it is
merged and deployed to production staging. Tonight that meant PR #46 — two candidate-visible
identity defects — could only be verified against a LOCAL hosted build with a stubbed service.
That worked and was conclusive, but it is not the deployment.

Ways out, cheapest first:

* scope the non-secret variables (`AILX_BACKEND`, `NEXT_PUBLIC_AILX_BACKEND`,
  `NEXT_PUBLIC_AILX_API_BASE`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` — the last two are public by
  design) to Preview as well as Production;
* turn on Protection Bypass for Automation and hold the token where CI and an agent can read it;
* allow the project's preview wildcard origin in `AILX_ALLOWED_ORIGINS`, or point previews at a
  disposable service.

The third one is a deliberate security boundary and deserves the most thought — a wildcard there
is not free.

---

**Decision recorded 2026-09-05.** Not fixed tonight, deliberately. The three halves are not equally
cheap and should not be done in one patch:

* **The env scoping is independently fixable and the cheapest of the three.** Every variable is
  Production-only today. Scoping `AILX_BACKEND`, `NEXT_PUBLIC_AILX_BACKEND`,
  `NEXT_PUBLIC_AILX_API_BASE` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` to Preview as well would
  already turn a preview from "a different product" into "the same product it cannot phone home
  from". The last two are publishable by design, so nothing secret moves. Do this one first; it
  needs no security argument.
* Protection Bypass for Automation is a second, separate step.
* **Widening** `AILX_ALLOWED_ORIGINS` **to preview origins is a real security boundary and needs a**
  **decision, not a patch.** A wildcard there is not free. A disposable service for previews is the
  alternative worth costing.
