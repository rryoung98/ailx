# TEN-249 — [P2] The runtime service account holds project-level secretAccessor, so the public API can read every secret
status: Backlog
url: https://linear.app/tenken/issue/TEN-249/p2-the-runtime-service-account-holds-project-level-secretaccessor-so

**What breaks.** The service account that serves anonymous public traffic has `roles/secretmanager.secretAccessor` at the PROJECT level, not per secret. Any code execution or SSRF in the API image reads every secret in the project, including the one that seals every candidate's provider key. The correct pattern already exists next door: the deployer's grant is per secret.

**Evidence.**

* `infra/terraform/main.tf`, resource `runtime_secret_accessor`: the binding is on the project, not on individual secrets.
* Secrets in reach: `ailx-provider-key-secret` (seals every stored provider key under AES-256-GCM), `ailx-clerk-secret-key`, `ailx-judge-api-key`, `ailx-github-token` (a repo Contents write token), `ailx-database-url`.
* The deployer grant in the same file is scoped per secret, so the pattern is already understood in this repo.

**Blast radius.** Every stored provider key, the Clerk secret, the judge key and a GitHub write token, from one compromise of the public API image.

**How we know it is fixed.** The runtime grant is one `google_secret_manager_secret_iam_member` per secret the service actually reads, and `gcloud projects get-iam-policy` shows no project-level `secretAccessor` for the runtime SA.
