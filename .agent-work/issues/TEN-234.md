# TEN-234 — [P2] Every non-2xx on issue, create, publish and revoke is reported as a transient network blip
status: Backlog
url: https://linear.app/tenken/issue/TEN-234/p2-every-non-2xx-on-issue-create-publish-and-revoke-is-reported-as-a

**What breaks.** The three end-of-sitting write panels collapse a refusal and an unreachable service into one sentence and throw the status away. A 403, a 409 or a 429 all read as the network hiccuped, try again, so the candidate retries a permanent answer forever.

**Evidence.**
`apps/web/features/report/CredentialPanel.tsx:152-165` (`if (!res.ok) throw new Error(String(res.status));` then `catch { setPhase("error"); }`) with copy at `:218-222` (`That did not reach the exam service ... Try again in a moment.`). Same pattern at `features/report/ShareLink.tsx:257,281,293` with copy at `:106-110` and `:155-159`. The repo already models this correctly elsewhere: `lib/data/serviceFetch.ts:51-55` keeps `missing` (reached and refused, with status and reason) apart from `error`, and `serviceRefusedCopy` (`:75-81`) says which.

**Blast radius.** The three write actions a candidate performs at the end of a sitting, including issuing and revoking a credential.

**Fixed when.** The panels use the same refused/unreachable split, print the status and the service's reason, and do not offer a retry for a refusal that will not change. A 403 on issue and on create must not produce the try again in a moment wording.
