# TEN-192 — [P1] The people table aggregates the whole store on every page view
status: Backlog
url: https://linear.app/tenken/issue/TEN-192/p1-the-people-table-aggregates-the-whole-store-on-every-page-view

**What breaks.** `peoplePageSql` (`features/people/sql.ts`) leaves `matched` unfiltered when both parameters are NULL, which is the default view. `att` and `pr` then aggregate all of `attempts` and all of `practice_sessions` grouped by participant, and `count(*) OVER ()` runs over every matched row, before `LIMIT $3 OFFSET $4`. The comment above the function says the table must never fetch every participant. The rows returned are paged; the work is not.

**Evidence.** `features/people/sql.ts` `peoplePageSql`, the `matched`, `att`, `pr` and `page_rows` CTEs. The suffix predicate `auth_ref LIKE '%' || $1` also cannot use a b-tree, as the comment concedes.

**Blast radius.** `/people` is the first page to hit `statement_timeout` at scale, and it will render "the exam database refused the query", which reads as a broken deployment.

**How to know it is fixed.** Page `matched` first with a LIMIT inside the CTE, aggregate only the page, take the total as a separate cheap count. EXPLAIN the default statement against a seeded 100k participant table.
