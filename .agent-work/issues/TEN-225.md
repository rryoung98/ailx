# TEN-225 — [P1] The 'scanned at least one build output' sentinel in bundleSecrecy can never fail, so both bundle scans can silently degrade
status: Backlog
url: https://linear.app/tenken/issue/TEN-225/p1-the-scanned-at-least-one-build-output-sentinel-in-bundlesecrecy-can

**What breaks.** The sentinel that stops the secrecy gate becoming a green light is computed over MODES, and the third mode is the committed `apps/web/public` tree, which always exists. So `present` is never empty, the sentinel always passes, and if a CI build step or an output path ever moves, both build-output scans skip while the test file still reports success.

**Evidence.**
`apps/web/test/bundleSecrecy.test.ts:75-87` lists three modes; the third is `apps/web/public` (committed). `:397` `const present = MODES.filter((mode) => existsSync(mode.dir));` and `:425` `it.skipIf(present.length === 0 && process.env.CI === undefined)("scanned at least one build output", ...)`. Per-mode scans use `const run = existsSync(mode.dir) ? describe : describe.skip;` (`:436`), so a missing `out` or `.next/static` is a skip, not a failure. Verified by reading the file at the lines quoted. Second hole in the same file: it cannot tell a hosted `.next/static` from a static export's; `bundleBudget.test.ts` uses a `card.png` marker for exactly that distinction and `bundleSecrecy` does not.

**Blast radius.** The gate that keeps the operational answer key out of a public bundle. It scanned only build output until <issue id="8915b6f3-cbd0-43e5-97ac-b84e456ef310" href="https://linear.app/tenken/issue/TEN-117/bundlesecrecytestts-cannot-see-appswebpublic-or-any-non-js-file">TEN-117</issue>; this makes the reverse failure invisible. A rename of a build path turns a P0 secrecy gate into a no-op with the suite green.

**Fixed when.** The sentinel counts only modes with `expectItemIds: true`, a missing build output fails in CI rather than skipping, and a test asserts the sentinel fails when neither build directory exists.
