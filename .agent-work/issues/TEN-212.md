# TEN-212 — [P1] A model call cannot time out or be cancelled, so a hung request burns the track clock behind a disabled button
status: Backlog
url: https://linear.app/tenken/issue/TEN-212/p1-a-model-call-cannot-time-out-or-be-cancelled-so-a-hung-request

**What breaks.** None of the three model request paths carries a signal or a timeout. The callers set a busy flag cleared in `finally`, so a stalled provider leaves the controls disabled for the rest of the track while the clock runs to zero, with no cancel.

**Evidence.**
`packages/tracks/t1-creative-build/src/openrouter.ts:218`:

```ts
res = await fetchImpl(chatCompletionsUrl(baseUrl), buildFetchInit(payload));
```

`packages/tracks/t4-generative/src/imagegen.ts:163` is the same shape, and `apps/web/lib/data/modelGateway.ts:170` adds identity headers and nothing else. Repo grep for `AbortController` in `apps/web` and `packages/tracks` finds it only in `lib/data/funnel.ts` and `lib/data/serviceFetch.ts`, neither on this path. Busy flags: t1 `Runner.tsx:442`, t4 `Runner.tsx:322`.

**Blast radius.** T1 and T4 candidates on any provider stall. <issue id="fb728b72-c791-49d2-9cd4-dc764248487a" href="https://linear.app/tenken/issue/TEN-116/a-hosted-deck-fetch-that-hangs-or-fails-burns-the-whole-track-budget">TEN-116</issue> established that our own stalls must not be charged to the candidate; a stalled model call is charged in full and is not revisitable.

**Fixed when.** Model requests carry a timeout and a cancel control, a stall renders an explicit `the model did not answer` state, and a test with a never-settling fetch asserts the track is not silently burned.
