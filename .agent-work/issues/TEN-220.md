# TEN-220 — [P1] A stored log that fails to replay from entry 0 returns null, so the candidate silently starts over with no notice
status: Backlog
url: https://linear.app/tenken/issue/TEN-220/p1-a-stored-log-that-fails-to-replay-from-entry-0-returns-null-so-the

**What breaks.** `loadAttemptValidated` distinguishes a truncated log from a missing one, except when everything is dropped. If the first entry fails to replay, or the JSON is corrupt, it returns `null`, which the caller cannot tell from `there was no run`. The candidate's whole stored sitting is discarded and `persistNotice` never fires.

**Evidence.**
`packages/session/src/persist.ts:183`:

```ts
const validated = validateStoredLog((parsed as PersistedShape).log);
if (validated.log.length === 0) return validated.dropped > 0 ? null : validated;
```

Same silent null on a parse failure at `:170-174`. `loadAttempt` collapses both again at `:188-190` (`if (v === null || v.log.length === 0) return null;`). The truncation notice added in 34ca85c (`apps/web/features/exam/persistNotice.ts`, tested by `apps/web/test/legacyRunLog.test.tsx` and `packages/session/test/legacyLog.test.ts`) covers the partial case only: `dropped > 0` with an empty log is exactly the case it cannot see.

**Blast radius.** Any candidate whose stored log opens with an entry this build cannot replay: a schema change across a deploy, a partial write, an eviction mid-write. Their work disappears with no sentence, which is the defect class the truncation notice exists to end.

**Fixed when.** A fully dropped log produces the same visible notice as a partial truncation (a distinct return, not null), with a test that feeds a log whose first entry is unreplayable and asserts a notice rather than a silent fresh start.
