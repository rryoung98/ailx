# TEN-240 — [P1] The judging lease is not atomic: SELECT FOR UPDATE SKIP LOCKED runs outside a transaction
status: Backlog
url: https://linear.app/tenken/issue/TEN-240/p1-the-judging-lease-is-not-atomic-select-for-update-skip-locked-runs

**What breaks.** `claimAttemptForJudging` issues `SELECT ... FOR UPDATE SKIP LOCKED` with no `BEGIN`, so the row lock is released at statement end, and the `UPDATE` that marks the row `running` is a separate statement. Two runners can claim the same attempt and pay the jury twice. The lease duration makes it likely rather than theoretical: `LEASE_MS` is 600000 and the scheduler cron is `*/10`, while the worst-case pass is 2 tracks x 3 jury x 3 attempts x 120 s = 2160 s, which is 3.6x longer than the lease.

**Evidence.**

* `packages/backend/src/judging/queue.ts:157-186`: the `SELECT ... FOR UPDATE SKIP LOCKED` and the `UPDATE` are separate statements with no surrounding transaction. `withTransaction` exists at `packages/backend/src/db.ts:19` and is not used here.
* `packages/backend/src/judging/queue.ts:76` `LEASE_MS = 600_000`; `infra/terraform/variables.tf:460-470` sets the drain cron to `*/10`.
* `services/api/src/judging.ts:103-106` asserts this cannot happen.
* Live: `judging_runs` is empty, so the path has never been exercised against real concurrency.
* The unique keys on `judgments` and `scores` stop a duplicate ROW, but they do not stop the duplicate model CALL, which is the bill.

**Blast radius.** Duplicate judge spend on every attempt that two runners race on, and duplicate rows if the gateway echoes a different model id (see the related model-id finding).

**How we know it is fixed.** The claim is one statement or one transaction, `LEASE_MS` exceeds the worst-case pass duration, and a test starting two runners against one queued attempt shows exactly one model call.
