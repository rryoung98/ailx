# TEN-246 — [P1] T3 transcript order is candidate-supplied seq, so a back-filled turn buys verification credit
status: Backlog
url: https://linear.app/tenken/issue/TEN-246/p1-t3-transcript-order-is-candidate-supplied-seq-so-a-back-filled-turn

**What breaks.** T3 credit is order-sensitive and the order is `transcripts.seq`, which the candidate supplies for their own turns AND for the server-written `assisted` row. A candidate can insert a turn at an earlier free seq after the fact and buy credit for deliberation that never happened. `server_ts` exists in the schema and is never read. The store's own comment gives exactly this reason for not trusting `client_ts`, then orders by a column that is equally candidate-supplied.

**Evidence.**

* `packages/backend/src/store.ts` `getTranscripts` orders by `t.seq, t.id`. Its doc comment: "`client_ts` is candidate-supplied and a candidate who could reorder their own transcript could turn a blind accept into a deliberated one".
* `packages/backend/src/handlers.ts` `handleAppendTranscript` passes `b.seq` straight through; `store.ts` `assertSeq` checks only the integer range.
* `packages/backend/src/handlers.ts` `handleT3Assist`: `const seq = typeof b.seq === "number" && Number.isInteger(b.seq) && b.seq >= 0 ? b.seq : nextSeq(rows);` The client names the position of the row the SERVICE writes as its own evidence.
* `packages/track-t3/src/scoring.ts` `verificationTally` is index-order dependent: `const answerFinalAt = submittedAt < 0 ? transcript.length : submittedAt;`, `if (raisedAt === undefined || i <= raisedAt) return;`, `if (!stance || stance.at <= checkedAt) continue;`.
* Concrete sequence: post `assisted` at seq 10, `accepted` at seq 20, then insert `verified` at seq 15. The check now precedes the stance and counts as a discriminating verification.
* `transcripts.server_ts` is written and never read by any query in `packages/backend/src`.

**Blast radius.** Every T3 sitting, the 35-point Process component, and the reported reliance behaviour. This is a scoring-integrity defect on the store's central claim: only rows a request body cannot write are proof.

**How we know it is fixed.** The order scoring reads is server-observed (`server_ts` or a server-assigned monotonic sequence), the assist route stops accepting `b.seq`, and a test that appends a back-filled `verified` row asserts the tally does not move.
