# TEN-252 — [P2] Append-only is application discipline: the runtime connects as the table owner
status: Backlog
url: https://linear.app/tenken/issue/TEN-252/p2-append-only-is-application-discipline-the-runtime-connects-as-the

**What breaks.** The README calls `responses`, `transcripts` and `judgments` append-only. Postgres does not know that. There is exactly one trigger in the whole schema and it is unrelated, every table is owned by the same role the service connects as, and there is no INSERT/SELECT-only runtime role. The invariant is a code convention, and the code is one review away from breaking it.

**Evidence.**

* Live `pg_trigger` in schema `public`: exactly one trigger, `scores_track_recorded`. No append-only enforcement trigger and no rule exists on any table.
* Live `pg_roles`: only four login roles; only `ailx_admin_ro` is SELECT-only. All tables are owned by `neondb_owner`, and the service connects as the owner.
* Live `pg_stat_user_tables.n_tup_del` is non-zero on tables the README calls append-only or stable: `responses` 341, `attempts` 54, `participants` 52 (from migration `0008`, which does copy verbatim to `archive.*` first and has a working Down).
* The application half is clean: `grep` for `UPDATE`/`DELETE` against `responses`, `transcripts`, `judgments`, `practice_answers` or `moderation_comments` in `packages/backend/src` returns nothing. That is discipline, not a constraint.

**Blast radius.** The store's central claim. An auditor cannot verify append-only from the database alone.

**How we know it is fixed.** The service connects as a role with INSERT and SELECT only on the append-only tables (UPDATE granted per column where a lifecycle stamp needs it), and a manual `DELETE FROM responses` as the runtime role is refused.
