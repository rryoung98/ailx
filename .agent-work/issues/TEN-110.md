# TEN-110 — HIGH: the served score is the candidate's mirrored number, not the score of record
status: Backlog
url: https://linear.app/tenken/issue/TEN-110/high-the-served-score-is-the-candidates-mirrored-number-not-the-score

From the 2026-09-04 backend review (/Users/rickyyoung/GitHub/ailx-backend-review-2026-09-04.md, finding **C1**, BUG/HIGH).

Every candidate-facing and PUBLIC surface derives its number by projecting the candidate's own mirrored session log. No surface reads the `scores` table.

* `packages/backend/src/aggregates.ts:39-52` + `shapeOf` at `:81-89` -> `collectWorldAggregates` (`:138`) -> `handleWorldAggregates` (`:163`), an **unauthenticated public statistic**.
* `packages/backend/src/share.ts:136` -> `:188` `buildSharePayload`; `packages/report/src/share.ts:219,224,269` freeze `band` and the four per-track numbers into the share payload. Gallery and moderation cards read that payload (`gallery.ts:139`, `moderation.ts:113`).
* `packages/backend/src/practice.ts:391-397` — the personal progression chart.

The candidate can write those rows: `appendResponse` accepts any JSON payload on their own open attempt (`store.ts:682-686`).

**Impact.** A candidate can publish a fabricated band/score on their share card and gallery entry, and move the public world aggregate. The service DOES issue a real score row (`finalize.ts:280-318`, `judging/worker.ts:374`) and never compares the two. `scoredBy` never leaves `finalize.ts:287` — grep finds it nowhere in `@ailx/report`, so the served payload carries no provenance label either. The only mitigation in code today is a comment calling the aggregate "advisory" (`aggregates.ts:18-20`), which is not a property of the API.

**Fix.** Serve the `scores` row on every surface that states a number; failing that, exclude the mirrored number from the public aggregate and label it in the payload (not in a comment). Reconciling the two and recording disagreement would also satisfy the audit story.
