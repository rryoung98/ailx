# TEN-229 — [P2] A 200 that is not JSON tells the reader their own connection is broken
status: Backlog
url: https://linear.app/tenken/issue/TEN-229/p2-a-200-that-is-not-json-tells-the-reader-their-own-connection-is

**What breaks.** `res.json()` throwing on a 200 lands in the same catch as a thrown fetch, so a captive portal or a CDN error page makes the page say the service did not answer and to check your connection. The sentence for the real fact already exists and is never shown.

**Evidence.**
`apps/web/lib/data/serviceFetch.ts:188,196-200`:

```ts
const body: unknown = await res.json();
...
} catch {
  if (opts.signal?.aborted === true) return { state: "loading" };
  return { state: "error", message: SERVICE_ERROR_COPY };
```

`SERVICE_INVALID_COPY` (`:94-96`) is written for exactly this, and the module header forbids conflating the two. The existing test asserts only the state, not the message (`apps/web/test/serviceFetch.test.tsx:227-231`), so the wrong copy is green.

**Blast radius.** Cosmetic per page, but it sends every affected reader to an action that cannot help.

**Fixed when.** The HTML-on-200 test asserts `SERVICE_INVALID_COPY`.
